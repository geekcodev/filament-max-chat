# План: синхронизация участников чата в `laravel-max-client`

> Файл переносимый: он описывает работу **в репозитории `laravel-max-client`** (`/home/user/web/laravel-max-client`),
> а не в плагине чата. Здесь он лежит как рабочая память до переноса. Источник истины по API MAX —
> `../max-php-client/docs/api-reference.md`, разделы про `getChatMembers` и `POST /messages`.
>
> Статус на 2026-10-02: не начат. Плагин чата со своей стороны уже научился работать с чатами, у которых состава в
> `max_chat_users` ещё нет (nullable `user_id`, `LEFT JOIN` в поиске, fallback-подписи в UI). Без этого плана состав
> чата остаётся неполным: заполняются только те участники, чьи `user` приехали в апдейте.

## Проблема

Реестр чатов адаптера наполняется из апдейтов MAX. `PersistMaxChatListener` создаёт строку `max_chats` по
`bot_added`/`bot_started`/`bot_stopped`/`bot_removed` и добавляет связь в `max_chat_users` только для того пользователя,
который приехал в самом апдейте (`$update->user` либо `$update->userId`).

Из этого следуют две дыры:

1. **Состав группы или канала без собственных сообщений.** Бота добавили в группу из 50 человек — приехал апдейт
   `bot_added` без `user`, строка чата создалась, а `max_chat_users` пуста. `MaxChat::interlocutor()` возвращает `null`,
   поиск по участникам ничего не находит, и единственный источник состава — ручной `getChatMembers` из кода приложения.
   Идентификаторы таких чатов отрицательные, поэтому забыть про них легко.
2. **Участник, вошедший в чат позже.** Событие `user_added` не обрабатывается вообще, хотя `UpdateType::UserAdded`
   есть в enum ядра. Человек может писать в группу годами, и в реестре он не появится, пока не пришлёт апдейт с
   `user` (то есть практически — пока не отправит сообщение, и то только если апдейт придёт с объектом пользователя).

Дополнительно: `MaxUserProfileService` умеет обновлять профиль по **уже известным** идентификаторам
(`refresh(int|array $userId)` требует список), а `upsertFromMember(ChatMember)` пишет только `max_users` и не создаёт
связь `max_chat_users`. То есть даже зная `chat_id`, пакет не может сегодня записать состав чата.

Идентификаторы `chat_id` и `user_id` в MAX — int64 и бывают отрицательными, колонки реестра знаковые, в тестах нельзя
рассчитывать на положительные значения.

## Что нужно получить

Публичный метод адаптера, который по `chat_id` приводит состав чата в актуальное состояние, плюс вызов этого метода из
точек, где состав заведомо меняется. Плагину чата после этого ничего дорабатывать не нужно.

Предлагаемый контракт:

```php
// src/Services/MaxUserProfileService.php

/**
 * Синхронизирует состав чата: постранично читает getChatMembers() и
 * записывает участников в max_users и связи в max_chat_users.
 *
 * @return int сколько участников записано
 */
public function syncChatMembers(int $chatId): int;
```

Если сигнатура не нравится в этом виде, минимально приемлемый набор — два метода:

- `fetchChatMembers(int $chatId): array` — только чтение, пагинация `marker` + `count`, без записи;
- `syncChatMembers(int $chatId): int` — вызов чтения плюс `upsertFromMember()` и связь `MaxChatUser::updateOrCreate()`.

## Шаги реализации

1. **Чтение состава.** В `MaxUserProfileService` (или новом `MaxChatMemberSyncService`, если так чище по SRP) добавить
   постраничное чтение `getChatMembers()`: `marker`/`count`, размер страницы из конфига, выход по пустой странице,
   защита от бесконечного цикла, если `marker` не меняется. Ошибку API не глушить — бросать наружу, вызывающий код уже
   умеет логировать без payload.
2. **Запись.** На каждую страницу: `upsertFromMember($member)` в `max_users`, затем `MaxChatUser::updateOrCreate()` по
   паре `chat_id` + `user_id` (`member_status` — по аналогии с `PersistMaxChatListener`, бот помечается ботом, остальные
   активны). Аватар не трогать: `ensureAvatar()` остаётся отдельной задачей с троттлингом.
3. **Точки вызова.** В `PersistMaxChatListener` после успешного `upsertChat()`:
    - для `bot_added` и `bot_started`, когда `$update->user === null` — полная синхронизация состава;
    - новый случай `UpdateType::UserAdded` — добавить пользователя из апдейта в `max_users` и в `max_chat_users`; если
      апдейт пришёл без `user`, ограничиться связью по `userId` без профиля. Полную синхронизацию при `bot_started`
      делать всегда: это повод дешево догнать состав после простоя.
4. **Фон и троттлинг.** Синхронизация одного чата — это запросы к API, поэтому вызывать её из обработчика вебхука
   синхронно нельзя: вебхук MAX ждёт быстрый ответ, а состав канала на 500 человек — это десятки запросов. Варианты:
    - `ShouldQueue`-задача `SyncChatMembersJob` с `tries = 3`, вызывается из слушателя;
    - либо синхронно, но только если страница участников укладывается в лимит — тогда лимит задаётся конфигом, а остаток
      добирается по крону. Выбор — по фактическому лимиту API на чтение состава (проверить в `docs/api-reference.md`
      ядра). Ошибку задачи логировать без тела ответа.
5. **Конфиг.** Ручки рядом с существующими, без дублирования имён:
    - `MAX_CHAT_MEMBERS_SYNC` (`chats.members_sync`, по умолчанию `true`, но неактивно, пока `chats.enabled = false`);
    - `MAX_CHAT_MEMBERS_BATCH_SIZE` (`chats.members_batch_size`, по умолчанию 50);
    - при необходимости `MAX_CHAT_MEMBERS_TTL` (`chats.members_ttl`, по умолчанию 3600) — чтобы крон-команда
      `max-chat:sync-members` не опрашивала API без нужды. Всё это добавить в `.env.example` адаптера и в README раздела
      «Реестр чатов».
6. **Команда дозагрузки.** `php artisan max-chat:sync-members` — разовый проход по активным чатам из `max_chats` с
   `--chat=` для одного чата и `--force`, чтобы обойти TTL. Нужна миграции с 1.1.x на новую форму реестра: у
   существующих установок состав чатов неполный, и без ручного прохода данные останутся неполными навсегда.
7. **Удаление связей.** `UpdateType::UserRemoved` — удалять строку из `max_chat_users` (или помечать статусом), иначе
   ушедший из группы навсегда останется в интерфейсе чата плагина. Это отдельный случай, но логично закрыть вместе с
   `UserAdded`.

## Тесты

Юнит и feature в `laravel-max-client` по его же соглашениям (Testbench, очередь подменена, транспорт
`ClientInterface` мокается):

- `syncChatMembers()` пишет `max_users` и `max_chat_users` по данным первой страницы;
- вторая страница дочитывается по `marker`, `marker` не меняется — цикл прерывается;
- состав чата с отрицательным `chat_id` (канал) и отрицательным `user_id` сохраняется без потерь;
- повторный вызов идемпотентен: число строк не растёт;
- `bot_added` без `user` ставит задачу синхронизации, с `user` — не ставит;
- `user_added` создаёт `max_users` + `max_chat_users`, `user_removed` убирает связь;
- при `chats.enabled = false` слушатель не регистрируется, новый случай тоже ничего не делает;
- ошибка API не оставляет частично записанный состав: транзакция на страницу либо на весь вызов.

## Критерии готовности

- `composer test` в адаптере зелёный, покрытие не ниже текущего порога пакета, `composer security-audit` чист;
- новый публичный метод описан в README адаптера и в release-notes вместе с `UserAdded`/`UserRemoved`;
- `user_added` и `user_removed` отражены в разделе про события MAX, чтобы плагин чата и другие потребители знали, что
  адаптер теперь реагирует на них сам;
- релиз адаптера — minor, в notes есть строка о том, что состав чатов у существующих установок надо дозагрузить командой
  `max-chat:sync-members`.

## Чего делать не надо

- Не переносить эту логику в `filament-max-chat`: плагин тонкий слой UI и истории переписки, а состав чата —
  ответственность реестра (`AGENTS.md` §1 и §5 плагина).
- Не вызывать `ApiClient` из `filament-max-chat` напрямую ради обхода дефекта адаптера: по правилам репозитория
  регрессия чинится в пакете-источнике, а не обходом на стороне потребителя.
- Не делать состав чата обязательным для работы плагина: пустой `max_chat_users` — штатная ситуация, плагин её уже
  переживает.
