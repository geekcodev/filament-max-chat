# Порядок миграций: полоса `0000_02` вместо сдвига номеров

## Симптом

`php artisan migrate:fresh` в приложении падал на пустой базе:

```
SQLSTATE[42P01]: Undefined table: 7 ERROR: relation "max_chats" does not exist
```

## Причина

Laravel сортирует миграции приложения и всех пакетов по имени файла и применяет сверху вниз, поэтому внешний ключ
допустим только на таблицу, чья миграция имеет меньшее имя. Первая починка сдвинула номер плагина за `0002` адаптера,
но сохранила полосу «плагины после адаптера» и не зафиксировала правило: следующий пакет задал бы тот же вопрос.

## Решение: полоса по графу FK

Полоса в имени миграции — это позиция владельца в общем порядке, а не отдельный именованный диапазон. Раскладка
стека i2tech:

```
0000_00 — laravel-max-client: max_users, max_chats, max_chat_users
0000_01 — приложение, системные таблицы (users и прочие)
0000_02 — filament-max-chat
0000_03 — filament-max-broadcasts
0000_04 — приложение, доменные таблицы
```

Позиция плагина выведена из его собственных FK: `max_chat_messages.max_chat_id` ссылается на `max_chats` из
`0000_00`, `max_chat_messages.operator_id` — на `users` из `0000_01`. `0000_02` — единственная полоса после обеих.

Миграции (имена, под которыми они вышли в v1.1.0):

- `0001_01_01_000001_create_max_chat_messages_table` → `0000_02_000001_create_max_chat_messages_table`;
- `0001_01_01_000003_make_max_chat_messages_user_id_nullable` → `0000_02_000002_make_max_chat_messages_user_id_nullable`.

Промежуточный вариант (`0001_01_01_000004` и `0001_01_01_000005`, сдвиг за `0002` адаптера) не выходил в релиз, поэтому в
release-notes и в docblock миграций фигурируют только имена v1.1.0.

В `up()` обеих стоит `Schema::hasTable()` с выходом по `return`: после смены имени миграции числятся невыполненными
при уже существующей таблице, и без guard повторный `Schema::create` упал бы «таблица уже есть» — то есть ломается
ровно та установка, ради которой переименование и делается. Правило «миграции нельзя править на месте; переименовывать
можно только с guard» зафиксировано в `AGENTS.md` §5, подробность про `Schema::hasTable()` — в gotcha 21.

## Тесты

`tests/Feature/MigrationOrderTest.php` проверяет по исходникам, что миграции лежат в `0000_02` и что каждый FK ведёт в
более раннюю миграцию. Смысл именно в исходниках: на SQLite таблица с внешним ключом на несуществующую таблицу
создаётся молча, и ни один тест на SQLite такой дефект не видит. Регрессия проверена: перенос create-миграций плагина
в `0000_00` роняет тест на позднем `users`.

Тестовая фикстура `users` переименована из `0001_01_01_000000` в `0000_01_000000` — под полосу системных миграций
приложения.

Сквозную проверку по миграциям всех владельцев выполняет `MigrationOrderTest` в приложении: в vendor этого пакета стоит
установленная версия адаптера, чьи имена миграций меняются независимо, поэтому читать чужие файлы отсюда нельзя.

## Зависимость от адаптера

Полосы несамостоятельны: `0000_02` плагина работает только с адаптером, чьи миграции лежат в `0000_00`. На момент
сессии полоса `0000_00` у адаптера есть только в рабочем дереве `../laravel-max-client` (staged, не закоммичено): и
тег v1.2.0, и установленная в vendor версия держат `0001_01_01_000001..3`. То есть с released-адаптером v1.2.0 плагин
в `0000_02` встаёт **перед** ним, и регрессия чистой установки возвращается, а constraint в `composer.json` (`^1.2.0`)
такую комбинацию разрешает. Релизы полос должны выйти вместе, а constraint — поднять на версию адаптера с `0000_00`;
до этого релиз v1.1.1 плагина технически сырой. Требование зафиксировано в README «Требования», gotcha 21 и docblock
create-миграции.
